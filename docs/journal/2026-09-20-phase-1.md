## Difficultes rencontrees

(a completer au fil de la phase : symptome exact, cause, solution, temps perdu)

### Dependabot sans delai de refroidissement

**Symptome** : l'analyse de securite du depot a signale que la configuration Dependabot proposait
les mises a jour des leur publication.

**Cause** : par defaut, Dependabot ouvre une pull request des qu'une version parait. Une version
publiee depuis quelques heures peut etre instable, ou compromise par une attaque de la chaine
d'approvisionnement.

**Solution** : ajout d'un bloc `cooldown` avec `default-days: 7` sur chaque ecosysteme.

**Lecon pour le memoire** : a relier au chapitre sur les echecs, aux cotes de l'incident MinIO et de
Log4Shell. La dependance automatique n'est une bonne pratique que si elle est temporisee et verifiee
par une CI.

### Gitleaks ne detecte pas tous les secrets

**Symptome** : `make secrets` annoncait `no leaks found` alors qu'un faux secret venait d'etre
plante dans le depot pour tester l'outil.

**Cause** : deux problemes distincts. D'abord la cible du Makefile utilisait `gitleaks detect`, qui
ne lit que l'historique des commits : sur un depot sans commit, elle scannait zero octet. Ensuite,
meme corrigee, la detection depend du format du secret. Un jeton GitHub (`ghp_` suivi de 36
caracteres) est reconnu immediatement. Une cle secrete AWS, simple suite de 40 caracteres, ne l'est
pas, et l'exemple officiel de la documentation d'Amazon est meme ignore volontairement pour eviter
les fausses alertes.

**Solution** : la cible scanne maintenant les deux surfaces, `gitleaks dir .` pour les fichiers
presents et `gitleaks git .` pour l'historique.

**Lecon pour le memoire** : un scanner de secrets est un filet, pas une garantie. La protection
reelle vient de la defense en profondeur : configuration par variables d'environnement, `.env`
ignore par git, `.env.example` sans valeur reelle, scanner en pre-commit et en CI. A relier a
l'incident Samsung, ou du code confidentiel a fuite parce qu'aucune barriere n'existait en amont.

### Une protection de branche qui ne protegeait personne

**Symptome** : la protection de `main` etait bien enregistree par l'API GitHub, mais un push direct
sur `main` est quand meme passe. Un commit de test est arrive sur le depot public.

**Cause** : le champ `enforce_admins` etait a `false`. Ce reglage signifie que les administrateurs
du depot ignorent toutes les regles de protection. Etant proprietaire du depot, j'etais donc exempte
de ma propre regle : elle ne s'appliquait a personne.

**Solution** : la protection a ete levee le temps de remettre `main` sur le bon commit, puis
retablie avec `enforce_admins: true`. Le nouvel essai de push direct est bien refuse avec
`protected branch hook declined`. Le `--force`, lui, etait deja bloque meme pour un administrateur.

**Lecon pour le memoire** : un controle de securite doit etre teste, pas seulement configure. La
configuration repondait correctement a l'API, tout avait l'air en place, et pourtant la regle etait
inoperante. C'est exactement le schema de l'echec Louvois, ou les controles qualite existaient mais
avaient ete desactives, et celui de Knight Capital, ou un deploiement manuel a contourne la chaine.
Regle appliquee au projet : tout garde-fou est verifie par un essai reel qui doit echouer.

### Le cout de `strict: true` sur les pull requests

**Symptome** : les trois pull requests de Dependabot, toutes avec une CI verte, ont ete refusees a
la fusion : `the head branch is not up to date with the base branch`.

**Cause** : la protection de `main` exige `strict: true`, donc une branche a jour avec `main` au
moment de la fusion. Des qu'une pull request est fusionnee, toutes les autres deviennent obsoletes.

**Solution** : pour chaque pull request, `gh pr update-branch <n>`, attendre la nouvelle CI, puis
`gh pr merge <n> --squash --delete-branch`. Trois pull requests ont demande trois cycles.

**Lecon pour le memoire** : c'est un arbitrage a expliquer, pas un defaut. Sans `strict`, on fusionne
du code teste contre une version perimee de `main`, et deux changements corrects separement peuvent
casser une fois reunis. Avec `strict`, la garantie est reelle mais chaque fusion coute un cycle de
CI. Sur un projet a un seul auteur, le cout est negligeable. Sur un depot a forte activite, c'est un
point de contention connu, que les files de fusion (merge queues) resolvent.

## A retenir pour le memoire
