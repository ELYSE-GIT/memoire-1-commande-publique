## Difficultes rencontrees

(a completer au fil de la phase : symptome exact, cause, solution, temps perdu)

### Dependabot sans delai de refroidissement

**Symptome** : l'analyse de securite du depot a signale que la configuration Dependabot proposait
les mises a jour des leur publication.

**Cause** : par defaut, Dependabot ouvre une pull request des qu'une version parait. Une version
publiee depuis quelques heures peut etre instable, ou compromise par une attaque de la chaine
d'approvisionnement.

**Solution** : ajout d'un bloc `cooldown` avec `default-days: 7` sur chaque ecosysteme.

**Lecon pour le memoire** : a relier au chapitre sur les echecs, aux cotes de l'incident MinIO et de
Log4Shell. La dependance automatique n'est une bonne pratique que si elle est temporisee et verifiee
par une CI.

### Gitleaks ne detecte pas tous les secrets

**Symptome** : `make secrets` annoncait `no leaks found` alors qu'un faux secret venait d'etre
plante dans le depot pour tester l'outil.

**Cause** : deux problemes distincts. D'abord la cible du Makefile utilisait `gitleaks detect`, qui
ne lit que l'historique des commits : sur un depot sans commit, elle scannait zero octet. Ensuite,
meme corrigee, la detection depend du format du secret. Un jeton GitHub (`ghp_` suivi de 36
caracteres) est reconnu immediatement. Une cle secrete AWS, simple suite de 40 caracteres, ne l'est
pas, et l'exemple officiel de la documentation d'Amazon est meme ignore volontairement pour eviter
les fausses alertes.

**Solution** : la cible scanne maintenant les deux surfaces, `gitleaks dir .` pour les fichiers
presents et `gitleaks git .` pour l'historique.

**Lecon pour le memoire** : un scanner de secrets est un filet, pas une garantie. La protection
reelle vient de la defense en profondeur : configuration par variables d'environnement, `.env`
ignore par git, `.env.example` sans valeur reelle, scanner en pre-commit et en CI. A relier a
l'incident Samsung, ou du code confidentiel a fuite parce qu'aucune barriere n'existait en amont.
